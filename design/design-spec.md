## 0. このアプリは何か

**AIエージェント用のファイル（SKILL.md・CLAUDE.md・AGENTS.md など）を、iPhoneで「直す・決まりどおりか検査する・GitHubへ反映する」までできる、ただ1つのアプリ。**

普通のmdエディタとしても一通り使えるが、売りは次の3つ。

1. **その場で検査**：書いている最中に、Agent Skills の仕様や Claude Code の決まりに合っているかを1行ずつ判定し、直し方まで出す
2. **ひな形とフォーム**：SKILL.md の項目（name・description など）を入力欄で埋められる。決まりに合うひな形から作れる
3. **GitHubへそのまま反映**：変更を確認して、iPhoneだけでGitHubに反映（コミット）できる

### 0-2. 「ちゃんとできるか」の確認

| 機能 | できるか | 理由 |
|---|---|---|
| SKILL.md の検査 | **できる** | 決まりは公開文書に数値で書かれている（§8）。iPhoneの中だけで判定でき、通信も不要 |
| CLAUDE.md・AGENTS.md の検査 | **できる（範囲は限定）** | 取り込み（@path）の行き先の確認、行数の目安、同じフォルダに両方あるときの読まれ方など、文書に書かれていることだけを検査する。文の中身の良し悪しは判定しない |
| 文章量（トークン数）の表示 | **目安としてだけ** | AIが数える正確な数え方はiPhoneの中では再現できない。「約」と表示し、合否には使わない |
| GitHubへの反映 | **できる** | GitHubの公式の仕組み（REST API）で、複数ファイルをまとめて1回の反映にできる（§10-4） |
| 決まりが変わったとき | **アプリの更新で追従** | 検査ルールを「データ」として持ち、版番号を付けて管理する。仕様の更新を見張る作業は継続して必要（リスク） |

## 1. 前提

- アプリの目的：AIエージェント用のmdファイルを、iPhoneだけで正しく書いてGitHubに反映できるようにする
- 主な利用者と場面：
  - Agent Skills を GitHub で公開している人が、外出先で SKILL.md の説明文を直して反映する
  - Claude Code や Codex を使う人が、CLAUDE.md・AGENTS.md の決まりごとを追記する
  - 普通のmdファイル（README・メモ）を編集する
- 対応プラットフォーム：**iPhone / iPhone Duo / iPad**。Mac は「Designed for iPad」で動く想定で、Mac専用の画面は作らない（v1.0の範囲外）。Apple Watch は対応しない
- 掲載用画像：今回は作らない（App Store 提出時に別途）
- 画面の向き：iPhone は縦。iPad と iPhone Duo の内側は全方向
- 判断原則：標準の見た目 ＞ 片手で直せること ＞ 情報量
- HIG への準拠：Apple Human Interface Guidelines に従う。この設計書や実装の都合と HIG がぶつかったら HIG を優先し、どこがぶつかったかを報告する
- レイアウトの決め方：端末の種類や向きでなく、サイズクラス（実際に使える幅と高さ）で決める。iPhone は縦向き固定だが、Mac での iPhone ミラーリングや iOS 27 以降のシーンのリサイズで幅・高さが変わっても崩れないようにする
- ライト／ダーク：アプリ内に切り替えは作らず、本体の設定に従う。色はアセットカタログ（§3 のトークン）かシステムカラーだけで指定し、全画面をライト・ダークの両方で確認する
- 特に重視する HIG の原則：Purpose（目的がはっきりしている）、Agency（利用者が主導権を持つ）、Responsibility（勝手に反映しない・データを失わない）
- UI Kit の版：**未使用**（この環境では Apple Design Resources を開けないため）。寸法は hig-design-skill の `references/hig-specs.md` の値だけで描いた
- 起動画面：S-01 の骨格だけ（文字なし・ライト／ダーク別）
- 文言の管理：すべて String Catalog で管理する。**v1.0 から英語と日本語**。表示言語は本体の設定（アプリごとの言語設定を含む）に従う。全世界の App Store で売る（§17）
- デザインの方向：白黒ミニマル。余白の広い大きな角丸のカードと、画面ごとに1つの黒い横長ボタン。色は検査の記号だけ（§3）
- アプリアイコン：この設計の範囲外（別途作る）

- 下端に黒い横長ボタンがある押し込みの画面（S-17「試す」・S-18「切り出す」）：キーボードが出たら、ボタンをキーボードのすぐ上（間 8pt）に移す（キーボードのレイアウトガイドに合わせる）。S-17 の依頼文の Return キーは「試す」と同じ動作（表示は「実行」）
- 入力欄のラベルはプレースホルダとは別に、欄の上に常に出す（S-06「説明（必須）」、S-07「スキルの名前…」の形）
- 文字だけのボタン・リンク（S-05「根拠を見る」、S-09「購入を復元」「利用規約」「プライバシーポリシー」など）も当たり判定は 44×44pt 以上。S-09 の「利用規約」と「プライバシーポリシー」は1つの文にせず、別々のボタンにして間を 12pt 以上あける
- 一覧の節の見出し（モックの「GITHUB」「ON THIS IPHONE」「TEMPLATE」「CHANGES · 2」「EDITOR」「CHECKS」「DESCRIPTION」「EXPORT TO」「BEFORE EXPORT」「RECENT」「THIS IPAD」など）は表示言語で出す。日本語では「GitHub」「この iPhone」「ひな形」「変更（2）」「エディタ」「検査」「つないだ説明」「書き出し先」「書き出す前の確認」「最近」「この iPad」。英字の大文字の見出しは英語のときだけ

### 設定画面（S-10）

- エディタ：行番号を表示、補助キーの並び替え、自動保存（既定オン）
  - 文字の大きさは本体の設定（Dynamic Type）に従うので、アプリには置かない

## 4. プラットフォーム別の設計

### iPhone

- タブバーは移動専用。新規作成は右上の＋、反映は S-02 の下の黒いボタン
- エディタではキーボードの予測の段（キーの上の1段）に補助キーを並べる（inputAccessoryView ではなくキーボードの一部に見せる）。並びは「見出し # ／ 太字 ** ／ リスト - ／ チェック [ ] ／ コード ` ／ 字下げ → ／ 元に戻す」。横にスクロールでき、設定で並び替えられる
- 本文は白いカード（角丸30）の中。検査の結果はカードの下端に1行で出し（「12行目：リンク先がありません」）、押すと S-05 が開く。カードの下に黒い「完了」ボタン（キーボードを閉じる）
- 色は白黒だけ。注意（橙）と違反（赤）の印だけが色を持つ

### iPhone Duo

- 外側：S-03 は1段。ツールバー（戻る → プレビュー → …）を右端に縦に並べる。検査は本文のカード下端の1行から開く（iPhone・iPad と同じ。ツールバーに検査のボタンは置かない）。作業が中心の画面なので、タブバーは1つのボタンに畳む
- 外側の一覧（S-01・S-02）：移動が中心なので、タブバー（ファイル・最近・設定・検索）を右端に全部出し、ツールバーは 戻る → ＋ の順。入りきらない項目はあふれメニュー（…）へ
- あふれるときの優先度：残す順に 戻る ＞ ＋（新規作成）＞ プレビュー ＞ …。未反映の件数の印が付いた項目は最後まで残す
- ツールバーの各ボタンは、記号に加えて題名（「プレビュー」「新規作成」など）を持たせる（あふれメニューと VoiceOver で使う）
- 縦に並ぶバーの位置はシステムに任せ、独自に動かさない。右から左の言語でも同じ側（v1.0 は日本語と英語のみ）
- 内側（横向き）：左に一覧（S-02）、右に本文（S-03）。一覧の操作は一覧ペインの上、本文の操作とステータスバーは右端に縦。半分折ったときは左右均等にし、中央 ±13pt に操作・見出しを置かない（本文の行はかかってよい）
- 内側の縦向きは通常の横向きのバー。Split View（画面の半分）では外側と同じ1段の構成に戻る
- 開閉しても、開いているファイル・カーソル位置・入力中の文字を引き継ぐ
- 外側・内側の寸法、カメラとステータスバーの位置は Apple 未公開のため**近似**で描いた

### iPad

- 横向き：サイドバー（場所）＋一覧＋本文の3列。ツールバーの末尾に検索欄。強調する操作は「反映」1つで、iPhone と同じく一覧の列の下の黒いボタン（ツールバーには置かない）。⌘⇧R とメニューバーの「ファイル > 反映」からも使える
- 新規作成：一覧の列の上端の右に＋（横向きの3列でも細いウィンドウでも同じ位置）
- 細いウィンドウ：サイドバーを畳み、一覧だけを全幅に。先頭にウィンドウの3つの丸（近似）が出るので、丸と重なる位置にボタンを置かない（サイドバーの開閉ボタンは丸の後ろ）
- ポインタ：行・サイドバーの項目はホバーで背景を淡く（ハイライト）、ツールバーの丸いボタンはシステムのハイライトに任せる。独自のポインタの形は作らない
- キーボードショートカット：⌘N 新規作成、⌘S 保存、⌘⇧P プレビュー切り替え、⌘⇧L 検査結果、⌘⇧R 反映、⌘F 検索
- メニューバー（iPadOS）：ファイル（新規作成・反映）、表示（プレビュー・検査結果・サイドバー）にも同じ操作を入れる

## 5. アクセシビリティ

- VoiceOver の読み上げ順（S-03）：題名 → 本文 → 検査の1行（「注意1件。12行目、リンク先がありません」）→ 完了 → 補助キー
- 検査の各項目は「合格／注意／違反、項目名、内容、行番号」の順に1つにまとめて読ませる
- 記号だけのボタンのラベル（VoiceOver）：戻る＝システム、＋＝「新規作成」、eye＝「プレビュー」、pencil＝「編集」、…＝「その他」、xmark＝「閉じる」、checkmark＝S-06「反映」／S-07「作成」、虫めがね＝「検索」、サイドバー＝「サイドバー」、補助キー＝「見出し」「太字」「リスト」「チェックボックス」「コード」「字下げ」「元に戻す」（補助キーの並び §4 と同じ7つ）
- 検査の結果が変わったときの読み上げ：入力のたびには読まない。件数が変わったときだけ、入力が止まってから控えめな通知（「注意1件」）で知らせる
- Dynamic Type 最大（AX5）：S-02 の行は、名前を折り返し、補足を下の行へ移す。合格数は1行に1つずつ縦に並べ（6/7 → 合格 → 注意 N → 未反映 N。大きな数字と次の行が重ならないよう行の間をあける）、「N件の変更を反映」ボタンは全幅のまま文言を省略せず、文字を大きくして2行まで折り返し、ボタンの高さを広げる。エディタの行番号は AX3 以上では隠す
- タブバー・ツールバー・補助キー列は大きくしない。長押しで大きく表示する（Large Content Viewer）
- 「透明度を下げる」ではタブバーと丸いボタンを不透明に、「視差効果を減らす」ではシートの弾む動きを止める
- 新しい画面の読み上げ（監査で追記）
  - S-21 の版の行：「10時31分、3行追加、1行削除」。選んでいる行は「選択中」（isSelected の特性）。反映した版は「GitHub に反映した版」を末尾に足す。違いの行は「削除：…」「追加：…」と頭に付けて読む（＋−の記号は読ませない）
  - S-22：見本の欄は「取り込む文章」＋先頭200字。セグメントは「新しいファイル／今あるファイルに追記、2つのうち2番目、選択中」（標準のまま）
  - S-06-pr の注意の欄：「注意。main は保護されています。…」を1つにまとめて読む
  - S-05 の下の行：「除外中 1件、WR-01。押すと印の行へ移ります」（ボタンの特性）。検査ルールの版は別の要素として「検査ルール、2026年10月30日版」
- 新しい画面の最大文字サイズ（AX5）：S-21 の行は時刻を1行目、増減と「反映した版」を2行目へ。S-22 のセグメントは AX1 以上で2行のリスト（チェックマークで選ぶ形）に切り替える。S-06-pr のブランチ名は折り返す（省略しない。名前を確かめる欄のため）

- S-23・S-24 の読み上げ（監査で追記）
  - S-23 のカードの見本：画像1つとして読み、ラベルは成績カードの代替テキストと同じ文（§10-9）。棒や数字を1つずつ読ませない。セグメントは標準のまま
  - S-23 のバッジの見本：「バッジの見本。Skillwright、7項目中6項目合格」。README に貼る1行は「README に貼る1行」＋本文（URL を全部読ませる。ロータでの文字単位の確認ができる）。「1行をコピー」のあと、ボタンの文字を「コピーしました」に変え、VoiceOver に同じ文を通知する（時間で消える表示に頼らず、次の操作まで残す）
  - S-24 の時間：「経過 0分42秒、最長 5分」。毎秒は読まない（4:30 の「残り30秒」だけ通知）。波形は飾りなので読み上げから外す（accessibilityHidden）。録音中かどうかは時間の下の文「録音中」で伝える
  - S-24 の書き起こし：欄に移ったときに全文を読む（updatesFrequently の特性）。文字が増えるたびには通知しない。VoiceOver の読み上げの声がマイクに入って書き起こされるのを避けるため、VoiceOver がオンのときは録音を始める前に「イヤホンを使うと、読み上げの声が入りません」を1回出す。止めるボタンは「止めて作る」
  - 灰色の文字（まだ確定していない書き起こし）は見た目だけの区別で、読み上げでは区別しない
- S-23・S-24 の最大文字サイズ（AX5）（監査で追記）：S-23 のカードの見本は画像なので文字は大きくならない。押すと全画面で拡大表示（ピンチで拡大）し、内容は代替テキストでも分かる。設定の行（見た目・リポ名を出す）は名前と値を2行に分ける。S-24 の時間は64pt のまま大きくせず、書き起こしの欄は Body に従って大きくし、欄の中でスクロールして最新の行を見せる。止めるボタンと文言は下端に固定（ボタンの下の文字は2行まで折り返す）。録音後の見本は S-03 と同じく AX3 以上で行番号を隠す

### 長い文字・多い件数

- ファイル名・リポ名が長いとき：行では中央を省略（「very-long…name.md」）、画面タイトル（Large Title）は折り返す
- 件数の印（注意・違反）は3桁まで出し、それ以上は「999+」
- エディタの行番号の幅は桁数に合わせて広げる（5桁まで）
- S-06 の差分は1ファイル20行まで出し、続きは「すべての変更を見る（120行）」で開く。変更が50ファイルを超えたらファイル名だけの一覧にする
- 英語では文が長くなるので、ボタンは文字の幅に合わせ（固定幅にしない）、行の文は2行まで折り返す

### 検査の除外（全ファイル）

- 本文に次の印を書くと、その決まりを見ない。印は md のコメントなのでプレビューにも AI にも出ない（コメントとして本文に残る）
  - `<!-- skillwright-disable WR-01 -->`：このファイル全体で WR-01 を見ない
  - `<!-- skillwright-disable-next-line SEC-01 -->`：次の1行だけ見ない
- 違反（SEC-02 の鍵など）は除外できない。除外した決まりは S-05 の下に「除外中 2件」として残し、押すと印の行へ移る
- S-05 の各項目の … に「このファイルでは見ない」を置き、押すと印を自動で入れる
- 除外できないのは重さが「違反」の決まりすべて（SK-01〜07、CC-03・04・09、SEC-02 など）。違反の決まりを印に書いたとき・存在しない ID を書いたときは、その印の行に「情報：この印は効きません（理由）」を出す
- 合格数（6/7）の分母から除外した決まりは外す。「除外中 N件」の行は高さ44pt以上、末尾にシェブロン。N件が2件以上なら押すと一覧（決まりと行番号）を出し、選んだ行へ移る

### すべての md

| ID | 内容 | 重さ |
|---|---|---|
| MD-01 | 相対リンク・画像の行き先が存在する | 注意 |
| MD-02 | 見出しの段が飛んでいない（# の次に ### など） | 情報 |

- 検査ルールの配信：決まりは「値と文言のデータ（JSON）」だけを配る（文字数の上限、予約語、あいまい語の一覧、文言、根拠の URL）。新しい種類の判定の処理はアプリの更新で足す。データだけなので、App Store の決まり 2.5.2（アプリの機能を変えるコードを後から取ってきて動かさない）に触れない（ https://developer.apple.com/app-store/review/guidelines/ ）
  - 配る元は Cloudflare Workers（サインインの中継と同じ場所）。JSON に Ed25519 の署名を付け、アプリは同梱の公開鍵（CryptoKit）で確かめる。確かめられない・届かないときは同梱の決まりで動く
  - 確かめるのは1日1回まで（アプリを開いたとき）。決まりの版を S-10 に出す
  - 版の表示「2026.10.30」は日付でなく版の名前として扱う（地域設定で書式を変えない）
  - 取りに行くときに送るのは、今持っている決まりの版とアプリの版だけ（利用者の情報・ファイルの中身は送らない）。配る元の記録（アクセスの記録）は残さない設定にし、プライバシーポリシーとプライバシーの申告（データを収集しない）と食い違わないようにする
  - 新しい決まりで検査の結果が変わったときは、S-05 の下の版の横に「決まりが新しくなりました」を次に開いたとき1回だけ出す（結果が無言で変わらないように）
  - S-10 の「検査ルールの版」の行：押すと次の画面へ進み（シェブロンつき）、今の版・取得した日・同梱の版・「今すぐ確かめる」ボタン・変わった内容の一覧を出す
- 文の中身の良し悪し（「説明が分かりにくい」など）は合否にしない。内蔵 AI を使う判定（呼ばれ方テスト）は検査とは別の画面（S-17）で、目安として出す
- 検査の文言・あいまい語の一覧は英語と日本語の両方を持つ
- トークン数は「文字数からの目安」で、合否は「注意」まで（違反にはしない）

## 10. データ構造

### 10-1. ファイルの置き場所

- GitHub のリポ：アプリ内の `Workspaces/github/<owner>/<repo>/<branch>/` に、必要なファイルだけを取ってくる（丸ごと複製しない）
- このiPhone・iCloud Drive・ほかの場所：その場で開いて直接保存（ファイルアプリの仕組み）。ブックマークを保存して次回も開ける

### 10-2. 記録（JSON。`Workspaces/github/<owner>/<repo>/<branch>/.skillwright.json`）

```json
{
  "repo": "example-org/sample-skill",
  "branch": "main",
  "baseCommit": "<取ってきたときのコミット>",
  "files": {
    "SKILL.md": { "baseSha": "<GitHub側の版>", "localHash": "<手元の版>", "state": "modified" },
    "references/notes.md": { "baseSha": null, "localHash": "...", "state": "added" }
  }
}
```

### 10-3. 検査結果

```swift
struct LintIssue: Identifiable, Sendable {
  let id: UUID
  let ruleID: String        // 例 "SK-10"
  let severity: Severity    // .error / .warning / .info
  let message: LocalizedStringResource
  let range: Range<Int>?    // 行の範囲
  let fix: Fix?             // 自動で直せる場合の直し方
  let reference: URL        // 根拠の文書
}
```

### 10-4. GitHub への反映の流れ（GitHub の公式の仕組み）

1. 反映先ブランチの最新のコミットを取る。`baseCommit` と違えば、変更したファイルが GitHub 側でも変わっていないか確かめる（変わっていれば競合）
2. 変更したファイルごとにファイルの中身を登録する（blob）
3. ファイルの並び（tree）を作り、コミットを作る
4. ブランチの位置をそのコミットに進める（強制はしない。失敗したら競合として扱う）

- 保護されたブランチ（事実）：ブランチの情報に `protected` があり（ https://docs.github.com/en/rest/branches/branches#get-a-branch ）、ルールセットによる制限は「ブランチに効いているルールを取る」で分かる（ https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch ）。どちらも S-06 を開いたときに確かめる。ただしルールの種類の出方は文書に例がなく、確実ではない（不明）ので、**手順4が失敗したときも同じ流れに切り替える**
- 保護されていたら：手順3のコミットを新しいブランチ `skillwright/<ファイル名>-<月日時分>` に置き、プルリクエストを作る（ `POST /repos/{owner}/{repo}/pulls`、必要な権限は Pull requests の書き込み： https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request ）。題名は S-06 の説明文、本文はアプリが付ける短い説明。作ったら GitHub のプルリクエストの画面を開くボタンを出す
- GitHub App に「Pull requests：書き込み」の権限を足す（ https://github.com/settings/apps → このアプリ → Permissions & events → Repository permissions → Pull requests を Read and write）
  - 権限を足すと、すでにインストールした人は GitHub の画面で新しい権限を承認するまで使えない（GitHub App の仕組み）。承認前は S-06-pr の権限エラーの帯を出す（§2 状態ごとの画面）
- ブランチ名：`skillwright/<スキル名かフォルダ名>-<月日時分>`（例 `skillwright/tea-timer-10301042`）。変更が複数のファイルにまたがってもリポの中の1つのフォルダ名を使い、リポの直下ならリポ名。同じ名前があれば -2、-3
- レビュー依頼を出したあとの手元の状態（監査で追記・確認待ち）：反映した変更は「レビュー依頼中」として S-02 の行に印（arrow.triangle.pull、VoiceOver「レビュー依頼中」）を出し、「N件の変更を反映」の件数からは外す。押すと GitHub のプルリクエストを開く。次に GitHub から取ってきたとき、合わせる先にその変更が入っていれば印を消し、閉じられていたら「未反映の変更」に戻す
- 下書きとして出す：プルリクエストを draft で作る（ `draft: true` ）。S-06-pr のリストの行の中のトグル（既定オフ）

### 10-5. サインイン

- GitHub App を使う（触れるリポを利用者が GitHub の画面で選べる）
- 認可の画面は PKCE 付きで開く（GitHub は 2025-07 から PKCE に対応： https://github.blog/changelog/2025-07-14-pkce-support-for-oauth-and-github-app-authentication/ ）
- ただし、受け取った一時コードを鍵に換えるには「アプリの秘密の値」が要り、GitHub はアプリ側とサーバー側を区別しない。秘密の値をアプリに入れると抜き取られるので、**換える処理だけを Cloudflare Workers＋Hono の小さなサーバーで行う**（秘密の値はサーバーだけが持つ）
- 受け取った鍵はキーチェーンに保存し、アプリの外に出さない

### 10-6. 手元の版の履歴

- 保存のたびに、変わったファイルの中身をアプリ内の `History/<ファイルのID>/<日時>.md` に控える。同じ中身なら控えない
- 残す数：直近24時間は全部、それより前は1日1つ、30日を過ぎたら消す。GitHub に反映した版は印を付けて90日残す
- 「この版に戻す」は今の中身を控えてから入れ替える（戻したことも戻せる）。戻しても反映はしない
- iCloud Drive・ほかの場所のファイルも、控えはアプリの中に取る（元の場所にファイルを増やさない）
- 違いの向き：選んだ版を「戻したら、いまの版からどう変わるか」で出す（− がいまの版から消える行、＋ が戻ってくる行）。見出しは「10:31 の版に戻すと」
- 戻したあと：S-03 に戻り、上端に帯「10:31 の版に戻しました」＋「元に戻す」（次に入力するまで）
- 一覧の節：今日／昨日／日付（地域設定の書式）。30日分で多くても1ファイル約50行
- iPad・iPhone Duo の内側：S-21 は本文の列の中で押し込み（一覧の列はそのまま）。幅が regular のときは版の一覧を左、違いを右に並べ、「戻す」は違いの列の下端
- ファイルを削除したとき控えも一緒にゴミ箱の期間（30日）だけ残し、ゴミ箱から消えたら控えも消す

### 10-7. ほかのアプリとのつながり

- 共有シート（Share Extension）：文章・URL・md ファイルを受け取る。URL は自分では取りに行かず（v1.0）、ページのタイトルと URL をリンクとして入れる。本文の取り込みは v1.1 の「Web ページを references/ に保存」で行う
- ショートカット・Siri（App Intents）：「検査」（結果の件数を返す）、「新規作成」、「追記」、「未反映を反映」（Pro。説明文を受け取る。保護されていればプルリクエスト）。反映はアプリを開かずに動くので、実行の前に確認を出す
- 共有シートの追加の決まり（監査で追記）
  - 共有シートの中だけで完結させる（取り込んだあと Skillwright 本体を開かない。共有の拡張からほかのアプリは開けないため）。終わったら「取り込みました」を短く出して閉じ、S-02 の行に未保存でなく保存済みの変更として出る
  - 本体と拡張の間はアプリグループの共有の置き場所でファイルの一覧と控えを共有する。拡張のメモリの上限が小さいので、見本は先頭だけ読み、検査は本体を次に開いたときに行う（「入れたあと検査します」の意味。文言は「次に Skillwright を開いたときに検査します」にする）
  - 受け取る形：文章（public.plain-text）、URL（public.url）、md ファイル（net.daringfireball.markdown / public.text）。NSExtensionActivationRule に書き、画像だけの共有には出さない
  - iPad・iPhone Duo の内側では、拡張のシートはシステムのフォームシートの大きさ（独自の大きさにしない）
- ショートカットの追加の決まり（監査で追記）
  - 呼び出しの言葉（App Shortcuts）は英語と日本語で、アプリ名を必ず含む（例「Skillwright でこのリポを検査」「Check this repo in Skillwright」）
  - 結果と確認のスニペットは高さ400pt以下。確認のボタンは「反映」「レビュー依頼を出す」（「OK」にしない）。内容は反映先・ファイル数・説明を文字で出し、読み上げの文だけに頼らない
  - 無料版で「未反映を反映」を実行：課金の画面は開かず「反映は Skillwright Pro の機能です。アプリで購入できます」と返す。未連携・通信できない・競合は、§2 の帯と同じ文を結果として返し、手元の変更は消さない
  - 機密：結果の文に鍵やファイルの中身を入れない（件数と名前だけ）

### 10-8. 合格バッジ

- 公開リポだけで使える（非公開のリポではバッジの切り替えを出さず「非公開のリポにはバッジを付けられません」）
- バッジの数字はサーバー側で検査して出す（アプリが送った数字をそのまま信じない。偽の合格を作れないようにする）。サーバーは Cloudflare Workers（サインインの中継・ルールの配信と同じ）で、GitHub から公開のファイルを読み、**同じ検査ルールの JSON**で検査する
  - 検査の処理はアプリ（Swift）とサーバー（TypeScript）の2つになる。食い違わないように、同じ「入力の md と期待する結果」の組を両方のテストで使い、GitHub Actions で毎回確かめる
  - 結果はコミットごとに保存し、同じコミットは検査し直さない。GitHub を読む回数を抑えるため、新しいコミットの検査は1時間に1回まで
- 住所（仮。ドメインは未定、seventh-well.com の下に置く案）：バッジ `https://skillwright.seventh-well.com/badge/<owner>/<repo>/<フォルダ>.svg`、結果のページ `https://skillwright.seventh-well.com/r/<owner>/<repo>/<フォルダ>`
- README に貼る1行：`[![Skillwright](…/badge/…svg)](…/r/…)`。S-23 の「コピー」でこの1行を写す。「反映のときに README へ自動で入れる」切り替えも置く（既定オフ）
- バッジの見た目：白黒の2つに分かれた長方形（左「Skillwright」、右「✓ 7/7」）。違反があるときは右を「✗ 2」にし、色は付けない（shields.io の見た目に寄せるが、白黒）
- 結果のページ：合格・注意の一覧と、根拠の文書へのリンク。ファイルの中身は載せない（GitHub へのリンクだけ）。下に App Store へのリンク
- 監査で追記
  - バッジの文字は見る人の言語が分からないので英語だけ（「Skillwright」「✓ 6/7」「✗ 2」）。サーバーが検査できないとき（GitHub に読みに行けない・ファイルがない）は右を「?」にした白黒のバッジを返し、画像が壊れて見えないようにする
  - 「反映のときに README へ自動で入れる」：オンでも黙って入れない。S-06 の変更ファイルの一覧に README.md の差分（足す1行）として出し、ほかの変更と同じく利用者が確かめてから反映する。README.md がないときは作らず、切り替えの下に「README.md がないため入れません」。すでに1行があれば重ねて入れない
  - プライバシー：アプリはバッジのためにサーバーへ何も送らない（住所はアプリの中で作り、数字はサーバーが GitHub の公開のファイルから作る）。そのため App Privacy の申告は「データを収集しない」のまま。サーバーのアクセスの記録は残さない設定（§8 の配信と同じ）にし、プライバシーポリシーに「バッジのサーバーは公開リポのファイルを GitHub から読みます。アプリの利用者の情報は受け取りません」と書く
  - だれでも他人の公開リポの住所を作れるので、バッジは「そのリポの持ち主が付けた」ことを意味しない。結果のページに「Skillwright の決まりで自動で検査した結果です。Anthropic などのお墨付きではありません」と書く（誤解と審査の指摘を避ける）
  - S-23 のバッジの見本の下に、どの版の結果か（「GitHub の main・a1b2c3d・10:42 に検査」）を出す

### 10-9. 成績カード

- アプリの中で SwiftUI の ImageRenderer を使って画像にする。どこにも送らない
- 大きさは 1200×630（X などのリンクの見本と同じ横長）。ライト・ダークを選べる。リポ名を隠せる（既定は出す）
- 中身：スキル名、合格数（大きく）、AI からの見え方の3段の棒（起動時・呼ばれたとき・必要なとき）、文章量の目安、決まりの版、右下に小さく「Skillwright」
- 共有は標準の共有シート（ShareLink）。画像に説明の文（代替テキスト）を付ける
  - 監査で追記：共有シートで渡した画像には、代替テキストは付いて行かない（画像のファイルに説明の文を入れる標準の仕組みがない）。そのため ShareLink には画像と一緒に文（「tea-timer の成績：決まりに合格 6/7。起動時 約62・呼ばれたとき 約120・必要なとき 約240 トークン（目安）。Skillwright で検査」）を渡し、受け取るアプリが文を本文や代替テキストに使えるようにする。同じ文をアプリ内の見本の VoiceOver のラベルにも使う。「リポ名を出す」がオフのときは文からもリポ名を消す
  - カードの文字は表示言語で作る（日本語なら「決まり 2026.10.30」、英語なら「rules 2026.10.30」）。トークン数は「~62」でなく「約62」（英語は「~62」）
  - 「見た目」の行はプルダウン（ライト／ダーク、chevron.up.chevron.down）。既定は本体の見た目に合わせる
  - iPad・iPhone Duo の内側：S-23 は本文の列の中で押し込み（S-21 と同じ）。見本の幅は最大 480pt で中央に置く。半分折った内側の横向きでは、見本を右の半分に置き、中央 ±13pt にかけない

### 10-10. 声からスキル

- 書き起こしは Apple の SpeechAnalyzer（iOS 26 から。端末の中で動き、日本語・英語に対応。音声のモデルは OS が取ってくる）： https://developer.apple.com/documentation/speech/speechanalyzer ・ https://blog.addpipe.com/apple-speechanalyzer-api/
- 話した内容を、内蔵 AI（Foundation Models）の決まった形の出力で「name・何をするか・いつ使うか・手順・注意」に分け、SKILL.md のひな形に入れる。そのあと検査し、結果と一緒に見せる
- 内蔵 AI が使えないときは、書き起こしをそのまま「## 使い方」の下に入れ、name は空にする（検査で「name がありません」と出る）。画面にもそう書く
- 録音は最長5分。音声は保存しない（書き起こしの文字だけを残す）。マイクの許可を求める文：「話した内容から SKILL.md を作るために、マイクを使います。音声はこの iPhone の外に出ず、保存もしません。」
- 書き起こしの言語は表示言語に合わせ、録音画面で切り替えられる
- 監査で追記
  - マイクの許可を求める文の英語：「Skillwright uses the microphone to turn what you say into a SKILL.md draft. Audio never leaves this iPhone and is not saved.」（iPad では「この iPad」「this iPad」。String Catalog の InfoPlist で英日を持つ）
  - App Privacy の申告：音声と書き起こしは端末の外に出ないので「収集しない」。音声のモデルは OS が取ってくる（アプリの通信ではない）
  - 言語の切り替えは、書き起こしの欄の下の「日本語」を押すとプルダウン（日本語／English）。録音中は切り替えられない（淡色）
  - 作ったファイルの置き場所：「エディタで開く」を押した時点で初めてファイルを作る（できたあとの画面はまだ保存しない見本。カーソルは出さない）。S-02 から開いたときはそのフォルダの中に `<name>/SKILL.md`、S-01・ショートカットからはこの iPhone の中。同じ名前のフォルダがあれば -2、-3。name が空のとき（内蔵 AI なし）は `new-skill`。できたあとの画面の見本の下に「保存先」の行を出し、押すと S-07 と同じ保存先の選び方へ進む。作ったら S-03 で開き、未反映の変更として S-02 に出る（勝手に反映しない）
  - 内蔵 AI の結果の扱い（生成 AI の決まり）：見出しの下の文は「内蔵 AI が話した内容を項目に分けました。話していない内容が入ることがあるので、確かめてから使ってください。」。書き起こしの全文は「書き起こしを見る」（見本の下の文字のボタン）で見られる。やり直しは「やり直す」（録音から）
  - 確定の場所：S-24 はシートでなく全画面の作業（S-21 と同じ）なので、確定は下端の黒い横長ボタン「エディタで開く」1つ。「やり直す」は輪郭のボタン。閉じるは左上の xmark
  - 出し方：iPhone と iPhone Duo の外側は全画面（fullScreenCover）。iPad と iPhone Duo の内側はフォームシート。開閉しても録音と書き起こしは続ける。半分折った内側の横向きでは、左の半分に書き起こし、右の半分に時間・波形・止めるボタンを置き、止めるボタンを中央の折り目（±13pt）にかけない
  - ショートカット「声から作る」はアプリを前に出してから S-24 を開く（マイクはアプリが前にあるときだけ使える）
  - ＋からの入り方：＋は S-07 のシートを開くので、S-07 のひな形の一覧の末尾に「声から作る」（mic、線）の行を置き、選んだら S-07 を閉じてから S-24 を開く（モーダルを重ねない）

## 17. 全世界で売るための決まり

- 言語：英語と日本語を v1.0 から。文言はすべて String Catalog。日付・数・価格は本体の地域設定で表示（自分で書式を作らない）

- 検査の文言・あいまい語の一覧・ひな形（SKILL.md・CLAUDE.md・AGENTS.md）は英語版と日本語版を持つ。ひな形は表示言語に合わせ、切り替えもできる
